# Binary 设计

把常用命令行工具随服务一起分发：构建期把目标平台的预编译产物内嵌进服务可执行文件，运行期物化到临时目录，使沙箱内的子进程无需宿主预装、无需联网即可按名字调用。

## 目标与边界

- 沙箱内需要一个可预期的最小工具集，既不能假定宿主已安装，也不能在运行期下载；
- 做法是把预编译产物内嵌进服务可执行文件，运行期释放成真实文件——exec 只能执行文件系统中的文件，内嵌载荷必须先落地；
- 本文只覆盖“工具从哪来、如何变得可执行”；工具如何被执行归 [Process.md](./Process.md)。

## 工具集

| 工具   | 上游                 | 用途                            |
| ------ | -------------------- | ------------------------------- |
| `fd`   | `sharkdp/fd`         | 文件查找                        |
| `rg`   | `BurntSushi/ripgrep` | 递归搜索，默认尊重 `.gitignore` |
| `jaq`  | `01mf02/jaq`         | JSON 查询                       |
| `uv`   | `astral-sh/uv`       | Python 包与项目管理             |
| `uvx`  | `astral-sh/uv`       | 免安装运行 Python 工具          |
| `deno` | `denoland/deno`      | JS/TS 运行时                    |

- `fd`、`rg` 是核心工具，始终内嵌；
- `jaq`、`uv`、`uvx`、`deno` 是可选的运行时类工具，由构建选项按需内嵌，未启用则不进入产物；
- `uvx` 执行同目录的 `uv`，二者是绑定的一组。

## 内嵌方式

构建脚本从各上游 release 取与目标平台匹配的预编译产物，读出其中需要的可执行文件，压缩内嵌进服务：

- 只取预编译产物；目标平台没有对应产物即构建失败；
- 构建期需要网络，下载结果缓存复用，重复构建不重新下载；
- 压缩只用于减小服务体积。

## 物化模型

- 运行期把内嵌的工具释放成真实文件，落在系统临时目录下一个固定的子目录；
- 刻意选用固定的临时子目录：路径跨重启稳定，可被服务随后启动的沙箱引用；
- 该目录只承载可执行文件。

## 物化流程

- 服务启动时执行一次，早于对外服务；
- 每个工具并行展开；
- 先写同目录下的临时文件，赋予可执行权限后再原子替换到目标名：任何时刻对外可见的都是完整且可执行的产物，重复启动或并发物化都安全；
- 任一工具失败即整体失败。

## 启动接线

服务在开始监听之前完成物化；物化失败则启动失败。

## 与 exec 的契约

物化目录必须进入子进程的搜索路径，bare 名才能解析到内嵌工具：

- [Process.md](./Process.md) 的 exec、shell、pty 都以“单个可执行 token + 逐项 argv”启动，bare 名依赖路径搜索解析；
- 派生方以物化目录前置构造子进程的搜索路径，使内嵌工具可直接按名调用；
- 传入绝对路径时直接使用物化目录。

## 失败处理

内嵌产物在物化前已确定，运行期失败只可能来自文件系统：物化目录创建失败、单个工具落盘失败，或物化任务本身异常。三者一律向上暴露并终止启动。
